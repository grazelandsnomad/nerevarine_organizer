# 0.6 release notes

_In development._ Changes land here as they're committed; this file becomes the
GitHub release body when `v0.6` is tagged (release.yml reads it by version).

## New features

- **The Start button now checks that the script extender plugins can run.**
  A Bethesda game updates itself, you update the script extender and the
  address library along with it, and the game still dies at startup with
  "Unsupported address library format: 5" from a DLL it does not name. The
  address library ships one database per game version, each stamped with a
  format number, and a plugin compiled before that format existed refuses to
  read it. The plugins are what went stale, not the two things anyone thinks
  to update. Nerevarine reads the game's own version out of its executable,
  the format out of the database, and each plugin's build date and its record
  of whether it uses the address library at all - then names the mods, because
  the game's message names a file. On a real 1.7.99 profile that is eight mods
  listed and a ninth left alone: PrivateProfileRedirector scans for byte
  signatures instead and none of this touches it. Cancel or launch anyway, and
  a tick to stop asking for the session.

  Two more findings come free with reading those versions: a script extender
  built for a different game version than the one installed, and no address
  library at all for a profile whose plugins need one.

- **Bethesda profiles get the launch warnings at all.** The dialog above is
  the one OpenMW has always had, and the Start button for every other game
  went straight past it. Missing dependencies, mods that installed nothing and
  enabled forbidden mods are now reported there too.

- **The mod list shows which mod overwrites which.** When two enabled mods ship
  the same file only one copy actually loads: the one further down the list.
  Until now the list flagged that a conflict existed, with an orange "!" on the
  selected row, and never said who won. Every conflicting row now carries a
  green up arrow for what it overwrites, an orange down arrow for what
  overwrites it, and the counterpart named in plain words beside it
  ("overwritten by Amazing Companion Tweaks Spanish"). A mod caught in the
  middle shows both. Selecting a mod also washes its conflict partners in the
  colour of whoever wins, so the pair reads off the list without opening
  anything. Translations are the case this matters most for: a translated plugin
  ships the original's filename and only applies when it sits BELOW the mod it
  translates. Above it, it installs perfectly and is immediately overwritten,
  with nothing anywhere to say so.

- **Catch mods that collide without sharing a file.** A translation usually
  ships its plugin under its own name ("Better Crowd Citizens ES.esm" next to
  "Better Crowd Citizens.esm"), so nothing overwrites anything and the file
  view stays quiet - while both plugins deploy, both load, and both rewrite the
  same records. Plugins are now read for the records they override, and a row
  whose plugin rewrites the same records as another says so: *same 332 records
  as Better Crowd Citizens*. The right-click menu offers to disable the other
  one, which is normally what you want when a translation duplicates its
  original. Only records that override a master are compared, since a plugin's
  own new records are renumbered per load order and can never collide. The read
  seeks through record headers rather than loading the file, and Morrowind
  plugins are rejected on their magic, so an OpenMW list pays nothing for it.

- **Fix a wrong overwrite order from the row itself.** Right-click a conflicting
  mod for a **File conflicts** submenu listing every mod it shares files with.
  *Overwrite "X"* moves it directly below X so its files win, *Let "X" overwrite
  this* is the reverse, and *Go to "X"* selects and centres the counterpart. The
  mod moves next to its counterpart rather than swapping the two rows, so the
  rest of a curated order stays untouched even when the pair sits hundreds of
  positions apart. It behaves like any other reorder: undo works, the order is
  saved, and the arrows update once the rescan lands.

  The two kinds of conflict, and why a translation needs a different fix
  depending on how its author named the plugin, are written up in
  [`docs/conflicts.md`](../conflicts.md).

- **BAIN archive installer.** Mods packaged the Wrye Bash way - content split
  into numbered folders like `00 Core`, `01 Optional Textures`, `10 Alternate
  Meshes` - now get a package picker at install time instead of installing as
  one blob. The picker opens on a one-click choice - **Install everything** (the
  usual answer, and exactly what an install-all mod like Tamriel Rebuilt wants)
  or **Choose packages…** to tick a subset - and the chosen packages are merged
  into the mod. Re-installing or updating a BAIN mod remembers the packages you
  picked last time and pre-ticks them. FOMOD installers still take precedence;
  this only kicks in for the numbered-folder layout.

- **The download picker says what each file on the mod page is.** Choosing a
  file used to mean choosing between bare filenames. Rafael's Shader Pack
  offers a 22.4 MB main file, a 2.3 MB "Enhanced PBR Lighting" file and a
  "Patch For Enhanced PBR Lighting", all at the same version, with nothing on
  screen to say that the first is the mod, the second is a separate thing the
  page also hosts, and the third installs a fragment of a mod unless you take
  the second as well. Every row now carries a few words saying which it is,
  and a panel under the list explains the selected one in full - including the
  author's own note about that specific file, which the manager was reading
  from Nexus and throwing away. A patch is matched to the file it patches by
  name, so it can say which one it needs rather than just that it needs
  something. The opening selection is the mod page's own main download, and
  never a patch.

- **And which of them was built for your copy of the game.** Skyrim's GOG
  release is not the Steam release with the DRM removed, it is a different
  executable, so anything that patches the exe ships twice: SKSE64's page
  carries a "GOG" build and a "Steam" build and nothing else to tell them
  apart. The wrong one is the worst kind of mistake, because there is no error
  message - the game starts and everything that needed the extender is simply
  absent. Where a page offers a build per store, each row now says which store
  it is for, the one matching your copy is marked with a green tick, and it is
  what the picker opens on. The manager already knew the answer: the profile's
  own game path says whether the copy came from Steam or from GOG. The check
  needs two builds naming different stores before it says anything, so a mod
  named after Steam Deck is not mistaken for a store build, and a copy that
  came from neither shop is left alone rather than guessed at.

- **The FOMOD wizard answers its compatibility options from your modlist.**
  Plenty of installers offer "compatibility" options that exist for a different
  mod, and pre-tick them. An Addendum to Tamrielic Lore Data ships Ashfall
  meshes and a Glass Glowset option, all ticked - with neither of those mods
  installed, that quietly delivers meshes nothing will ever load, on top of
  files other mods may want. These options routinely link the mod they are for,
  right in their description, and a Nexus mod-page URL names one specific page,
  so it is matched against your modlist by id. An option whose mod is missing
  is now unticked and says so on its own label; an option whose mod you have is
  ticked and says which one. Options that link nothing are left exactly as the
  author set them, so ordinary options stay untouched - and no option is ever
  locked, so you can tick one back for a mod you keep outside the manager, or
  are about to add. In an exclusive group, where unticking means picking
  something else, the options are labelled but the choice stays yours. The same
  verdict outranks the choices remembered from your last run of that installer:
  those were made against a different modlist, and the label would otherwise
  contradict the tick right beside it.

- **Merge optional downloads into an installed mod.** Some mod pages ship
  optional files that are meant to override the main download (OAAB Data's
  optionals, for example). When you download an optional file for a mod you
  already have installed, the "already installed" prompt now offers a third
  choice - **Merge into existing** - alongside Replace and Install separately.
  Merge overlays the new files on top of the existing mod folder, letting them
  override the current ones (last writer wins), so the override lands in the
  same mod with no second entry to juggle in the list - the equivalent of
  Mod Organizer 2's merge. Replace (treat as an update) and Install separately
  (a different file from the same page) behave as before.

- **Share a mod between modlist profiles (no second copy on disk).** When you
  run more than one modlist profile for a game - say a "main" Morrowind list and
  a "StarWind" total conversion - right-click an installed mod and pick **Share
  with profile…** to add it to another profile pointing at the *same* installed
  folder. No files are duplicated. You choose whether to copy your current
  configuration (enabled state, FOMOD choices, notes) or start it disabled at
  defaults, and from there each profile's settings, load order and toggles
  diverge independently. Shared mods are tagged in their tooltip. Removing or
  uninstalling a shared mod from one profile keeps the files on disk while any
  other profile still uses them; the files are only deleted when the last
  profile lets go. And if you reinstall, update, re-run a FOMOD wizard on, or
  merge into a shared mod in one profile, it automatically forks a private copy
  for that profile first - so your change lands only where you made it and the
  other profiles keep their version untouched.

- **Share or back up a modlist as a single file.** **Export Modlist** now
  writes the list in the manager's own lossless format - load order,
  enabled/disabled state, FOMOD and BAIN package choices, Nexus links, your
  notes and separators all included - and **Import Modlist** reads it back
  faithfully. Paths are remapped on import and mods are matched by their Nexus
  link, so the same file works as a personal backup, as a way to move a setup
  between machines, or to hand your whole load order to someone else - anything
  they don't have yet imports as a placeholder to download or point at. (The
  previous export only captured names, paths and links; older exports still
  import.)

- **Enderal support.** Both editions of the Skyrim total conversion - **Enderal:
  Forgotten Stories** and **Enderal Special Edition** - now appear in the game
  switcher as their own games, with their own profiles, modlists, load orders
  and Nexus downloads (nxm links from the Enderal Nexus pages route straight to
  them). They're standalone Steam titles with their own save and config folders,
  so nothing overlaps with a Skyrim install. The Special Edition also gets the
  experimental deploy support (plugins list, SKSE launch detection), same as the
  other Bethesda titles below; the original stays download-and-organize only.

- **Find the mods your language pack never covered.** A new toolbar toggle,
  next to the overwrite one, marks every mod whose in-game text nothing in your
  list translates. Playing in Spanish, French or anything else, the awkward part
  was never installing the translation - it was knowing which of 200 mods the
  translation actually reached. The list now says so directly: **no
  translation** in red on a mod carrying text nothing covers, and **N of M
  strings untranslated** where a translation exists but leaves part of the text
  alone, which is what an outdated one looks like. Hovering names the partner
  mod, the plugins involved, and examples of the lines still in the original
  language.

  Mods with nothing to translate are never marked, so a mesh or texture pack
  stays silent even though it ships a plugin - what counts is whether the plugin
  carries text the player reads. Weapon, armour, book, spell, perk, container
  and message names count; NPC names, quest editor ids and cell names do not,
  since those are supposed to stay the same in every language. A pure replacer
  that only repoints models has nothing to say and is left alone.

  It works for any language, because it never tries to guess which language
  anything is in: it compares a mod's text against whatever else in your list
  rewrites the same records, and reports what stayed identical. That does mean
  it can tell you a translation exists without knowing it is *your* language.
  Proper nouns are counted too - "Riften" is "Riften" in Spanish - so a small
  number is normal, and the tooltip says so.

  Reading every plugin costs real time, so the toggle is off by default and the
  check only runs while it is on. Results are cached per plugin, so reordering
  the list re-decides coverage without re-reading anything.

- **Skyrim, split into the three games people actually mod.** The switcher used
  to offer "Skyrim Special Edition" and a plain "Skyrim", both hidden behind
  *Show all games*. There are now three entries, all reachable directly:
  **Skyrim Special Edition**, **Skyrim Anniversary Edition** and **Skyrim
  Legendary Edition (Oldrim)**. Each is a game of its own, with its own mods
  folder, modlist, load order and forbidden-mods list.

  Splitting SE from AE matters because the split is what the mods are built
  against: SE is pinned to runtime 1.5.97 and AE to 1.6.x, they need different
  SKSE builds, and most SKSE mods ship a separate file per runtime. Mixing both
  into one profile means one load order for two incompatible sets. Everything
  facing outward is still Special Edition's, because AE *is* SE plus the
  Creation Club content: the same folder, the same `SkyrimSE.exe`, the same LOOT
  game, the same Proton config dirs, and the same Nexus section - an AE profile
  asks Nexus for `skyrimspecialedition`, so mod links and the MO2 importer
  resolve normally. AE also gets the experimental deploy support and the
  **Tune INI** dialog, which previously matched on Special Edition's name alone.

  Oldrim is a genuinely different game - 32-bit, `TESV.exe`, its own Steam app,
  Nexus section, LOOT game, config folders and 32-bit SKSE - and is now named so
  it can't be mistaken for the others. It gets profiles, modlists, downloads,
  LOOT sorting and launching, but *not* the experimental deploy: Oldrim encodes
  load order in a third scheme (`plugins.txt` for what's active, `loadorder.txt`
  for the order) that this manager has no writer for, and guessing at one of the
  other two would deploy your mods and then load them in the wrong order. Same
  position as Enderal's original edition.

  If you have only one copy of Skyrim installed, SE and AE will both detect it
  and point at the same `Data` folder. Deploying from both would corrupt each
  other's backups, so deploying now warns when another game is aimed at the same
  folder. Give one of them its own copy of the game if you want to deploy both.

- **Dark Souls II support, including the wrapper mods Wine normally ignores.**
  Both editions can now be managed as games of their own, with **Dark Souls II:
  Scholar of the First Sin** in the game switcher. Souls games have no plugins
  and no `Data` folder: the engine reads whatever is in the folder next to the
  .exe, so "Deploy mods to game" links your enabled mods straight in there, in
  list order, backing up any original file it covers and restoring it when you
  remove the deployment.
  The part that matters on Linux is what happens next. A lot of Souls mods, the
  DS2LightingEngine path tracing mod among them, work by shipping a file named
  after a system library (`dxgi.dll` and friends) and relying on Windows
  loading the copy next to the game instead of its own. Wine does not do that,
  so on Linux those mods install perfectly and then do nothing at all. Deploying
  now also registers the DLL with the game's Proton prefix so Wine loads the
  mod's copy, tells you which ones it registered, and takes the setting back out
  again on "Remove deployed mods". An override you set yourself is left alone.
  Note that loose-file mods (retextures, model swaps) additionally need the game
  unpacked with UXM first, which this doesn't do for you. Wrapper mods like the
  path tracing one don't.

- **Cancel a stuck or slow install from the right-click menu.** Cancelling used
  to only work while a file was actually downloading - once a big mod hit the
  "installing…" phase (integrity check, then unpacking, which can run minutes
  for multi-gigabyte archives) there was no way out. The right-click menu now
  offers **Cancel Install** through the whole stretch: it stops the unpacker,
  cleans up the partial files, and puts the row back the way it was. Cancelling
  a queued or in-flight download works from the same menu as before.

- **A dependency graph, drawn from what you declared.** Dependencies were
  already stored and already editable, but only ever visible one mod at a time:
  double-clicking a row lists "Required mods" and "Required by", and nothing
  showed the shape. **Dependencies** in the toolbar opens a canvas of the whole
  web, arrows pointing from a mod to what it needs, so a chain like KID needs
  MergeMapper needs Address Library needs SKSE reads top to bottom instead of
  taking four dialogs to reconstruct. Boxes are draggable and where you put them
  is remembered per modlist profile; shift-dragging one box onto another adds a
  dependency, selecting an arrow and pressing Remove deletes one, and edits are
  applied through the same write path the "Required mods" dialog uses, so Ctrl+Z
  still undoes them. A dependency that matches nothing in your list is drawn as
  a missing box rather than quietly vanishing, a cycle is refused with the
  reason, and a mod with no Nexus page recorded says why nothing can point at
  it. As a list grows the whole web stops being readable, so a **section
  selector** narrows it to one separator at a time, showing every mod of that
  section whether it has a dependency yet or not. Whatever those mods point at
  is pulled in from its own section and drawn faded, because most dependency
  arrows cross a separator boundary (10 of 19 on the author's Skyrim list, 37 of
  38 on Morrowind) and a strict filter would cut every chain in half.

  Tune INI moved to the **Mods** menu, where it does the same thing it did in
  the toolbar.

## Bug fixes

- **Games installed through Heroic are found even when the folder is named
  something else.** Detection matched a store install only by the last part of
  its path against the folder names shipped for that game, so a GOG install of
  Gothic II sitting in "Gothic 2 Gold" was invisible while the shipped
  candidates read "Gothic II Gold Edition" and "Gothic 2 Gold Edition" - and
  setting up the profile went straight to a folder picker. Heroic's own library
  cache knew the answer all along; it is now read, so an entry is matched on
  its title and the store's folder name as well as the path. A second, looser
  pass folds roman numerals and drops edition words, and that one requires the
  game's .exe to actually be there before it counts, since Enderal and Skyrim
  Special Edition ship the same executable name. Steam now asks the app's own
  manifest where it was installed before guessing folder names, and Lutris
  matches its config files the same normalized way.

- **The app's own text was losing words, and sometimes whole sentences.**
  Translation files were read with Qt's configuration reader, which treats
  prose as settings: a semicolon ended the line, so "The modlist still saves;
  just without the sort step." shipped with the second half deleted; every
  comma-space came back as a bare comma, giving "(Flatpak,custom
  XDG_CONFIG_HOME,snap)"; and a quoted phrase lost both its quotes and the
  space next to it, so the conflict menu read "Let %1overwrite this" instead
  of `Let "Some Mod" overwrite this`. 174 strings were affected, 24 of them
  losing text outright, including one file dialog that silently lost its "All
  files" filter. These files are read as what they are now, and the strings
  arrive whole.

- **FOMOD Yes/No steps no longer invent a recommendation.** A step asking about
  the mod's own options - "Would you like the lanterns to use a glow effect?" -
  came back with "No. Recommended. This mod is not currently present in the
  modlist", which reads as a missing dependency being reported and pre-selected
  the wrong answer. A failed lookup only means something if the thing looked up
  was a mod name, and the modlist cannot establish that for a mod it does not
  hold. The verdict now needs evidence in both directions: a match in the
  modlist proves the step names a mod for the "you have it" half, and wording
  that asks after your setup ("Do you use X?", "for users of X", "Is X
  installed?") for the "you don't" half. A question about the mod's own options
  gets no verdict at all and keeps the installer's own default.

- **A failed unpack no longer leaves the row spinning forever.** When an
  archive failed to extract, the files were cleaned up but the mod's row kept
  its "installing…" spinner until the next app launch. It now resets to
  not-installed immediately, ready to retry.

- **A failed extraction no longer wrongly tells you to install 7z.** When a
  downloaded mod couldn't be unpacked, the error always ended with "Make sure 7z
  (p7zip-full) is installed" - even when 7z *was* installed and had clearly run
  (it exited with an error code, which only happens if it ran). The message now
  reflects the real cause: an extractor error code points at a corrupt or
  not-fully-downloaded archive and prompts you to re-download, and the "install
  it" hint only appears when the extractor genuinely can't be found.

- **Mods uploaded as a loose plugin now install.** Some mods (often small OpenMW
  ones) are uploaded as a bare `.omwaddon`/`.esp` file instead of inside a
  `.zip`/`.7z`. The installer always tried to *extract* every download, so those
  failed with a "7z fatal error". Downloads are now checked by content: a real
  archive is extracted as before, and a loose file is placed directly as a mod
  (named after the mod when the download itself carries no filename).

- **Downloads that arrive without a filename extension now install.** A few Nexus
  files come down named only as a bare ID with no `.zip`/`.7z` on the end, and
  installing one of those failed *every* time with a "7z fatal error" that looked
  exactly like a corrupt download - re-downloading never helped. The file was
  actually fine: the manager unpacks each download into a folder named after it,
  and with no extension that folder name collided with the downloaded file
  itself, so the unpacker couldn't create its output folder. The manager now
  always unpacks into a distinct folder, and these mods install normally. (Such a
  mod also used to land in the list under its raw download ID - e.g.
  `4c9017a6-…` - and now resolves to its proper Nexus title.)

- **Genuinely broken downloads are caught before the confusing extractor error.**
  When a download really is corrupt or incomplete, you used to get the same
  opaque "7z fatal error" at install time. Downloads are now sanity-checked as
  they finish - a truncated transfer, a server error page returned in place of
  the file, or an archive that fails an integrity test is detected, retried once
  automatically, and if it still won't come down cleanly the bad copy is kept
  (as `<name>.corrupt`) with a line written to a `download_diag.log` so the cause
  can be pinned instead of guessed. The clear next step - re-download, or grab it
  from Nexus and drag it onto the window - is shown instead of a cryptic code.

- **The window no longer freezes after installing or updating a mod.** Finishing
  an install/update used to lock the app up for a few seconds (the window greyed
  out, then recovered) - worst on a mods folder that lives on an NTFS/exFAT drive,
  where deleting the previous version's files is slow. The slow folder deletes now
  happen in the background instead of blocking the window: the old folder is
  vacated instantly and its files are cleared afterwards, so the list stays
  responsive. The mod's config (`openmw.cfg`/load order) is written exactly as
  before - only the cleanup moved off the main thread.

- **Updating a mod no longer leaves the old version sitting on disk.** Re-download
  or update a mod and the previous copy used to stay behind in your mods folder,
  right next to the new one. Do that across a big load order and you're quietly
  carrying gigabytes of versions you already replaced. Each mod now keeps a single
  folder: when a new one lands the old one is cleared out, unless something else in
  your list still points at it. There's also a new **Mods → "Clean Up Mod
  Folders"** that goes looking for leftovers from before this fix and offers to
  reclaim the space, and it shows you the whole list before it deletes anything.

- **Flatpak LOOT now works.** When LOOT is installed as a Flatpak, "Sort with
  LOOT" used to run it but it detected no plugins and closed - the Flatpak
  sandbox couldn't see your mods folders or the OpenMW config. The manager now
  launches Flatpak LOOT through `flatpak run` with the filesystem access it
  needs (mods/plugins on any drive, plus read/write to `openmw.cfg`), so sorting
  works the same as a native LOOT install. Native installs are unaffected.

- **Custom separator text colour is kept in dark mode.** 0.5's dark-mode
  separator theming darkened each section's background but also replaced your
  chosen *text* colour with a fixed light grey, so a separator you'd recoloured
  came back looking different after the update. Dark mode now keeps your text
  colour whenever it still reads against the darkened background, and only
  substitutes a light label when your colour would genuinely be unreadable
  (dark text authored for a pale background). Light mode was never affected, and
  no stored colours are changed - this is purely how they're drawn.

- **Separators no longer swallow a neighbouring section, and you get a say in
  where they land.** "Add Separator" used to insert just after the last-clicked
  row - and if that row was a *collapsed* separator, the new one dropped in
  among its hidden mods and silently adopted that whole section. Now "Add
  Separator" (Mods menu or right-click on empty space) always appends a fresh,
  empty separator at the **end** of the list, and right-clicking a row offers
  **Add Separator Above** to place one precisely above that mod. Drag it wherever
  you like afterwards as before.

- **Toolbar text stays readable on a dark desktop theme.** The Profile
  label/picker and the light/dark toggle button picked their text colour from
  the app's own light/dark flag. But "light mode" restores your desktop's
  native palette - which on a dark theme (e.g. Breeze Dark) is itself dark - so
  the app ended up painting near-black text on a dark toolbar. The text colour
  now follows the *actual* background, so those controls read correctly whether
  the underlying palette is light or dark.

## Experimental

- **Mod deployment for Bethesda games.** Early, opt-in support for managing games
  that aren't OpenMW: make a profile for one of the supported Bethesda titles and
  it gets **Mods → "Deploy to game"** and **"Remove deployed mods"**. Deploy links
  your enabled mods into the game's `Data/` folder (a hardlink, or a symlink or
  copy where a hardlink won't work), writes the plugin list, sets the load order
  the way that engine reads it, and edits the game's ini so its archives and loose
  retextures load. Everything is reversible - displaced game files are backed up
  and restored on "Remove deployed mods" - and re-syncs automatically before launch
  once you've deployed. This release started with OG Oblivion and now reaches
  **Fallout: New Vegas, Fallout 4 and Starfield** too, plus Fallout 3 once you turn
  on *Show all games*; the older Gamebryo titles and the newer Creation-engine ones
  each get the archive handling their engine needs. **It stays behind the game's
  own profile and doesn't touch your OpenMW/Morrowind setup.** Field-tested this
  release on a real Skyrim Anniversary Edition install, which drove a round of
  fixes and additions:

  - **Deployment runs in the background** with a centred progress panel over the
    list (a real percentage, not a spinner); the window stays responsive and the
    scan can be left to finish on its own.
  - **A banner says when your mods are not actually in the game.** These engines
    only load what is physically in `Data/`, so an installed-and-ticked list
    that was never deployed silently does nothing - the single most confusing
    part of managing a non-OpenMW game. A clickable notice now appears when the
    profile has never been deployed, or when the list changed since the last
    deploy; clicking it deploys.
  - **Script extenders now actually work.** SKSE-style mods put their loader
    beside the game .exe and their scripts in `Data/`; the loader half was
    silently dropped before. It is now deployed through a second, equally
    reversible manifest, and **Start launches the game through the script
    extender** (via the game's own Proton prefix) when one is present - the
    Launcher button keeps launching the official launcher.
  - **Mods shipping a bare `SKSE/` (or `Interface/`, `Strings/`, ...) archive
    root install correctly.** Address Library ships as nothing but
    `SKSE/Plugins/`; the installer used to dive into that folder and the files
    then deployed one level too shallow, which surfaced in game as "Failed to
    locate an appropriate address library" despite the file being on disk.
    Both the installer and the deploy now recognise Bethesda's `Data/`
    subfolder names, and older installs with the deep path deploy correctly
    anyway.
  - **A "Choose variant..." right-click entry** for mods that ship several
    alternatives and just expect you to copy one in (Main Menu Redone's
    wallpaper folders, for example - no FOMOD, no BAIN, so no installer ever
    asks). The chosen option's files are merged into the mod case-insensitively;
    picking again later replaces them.
  - Launch failures now say so instead of doing nothing, and the whole launch
    flow writes to the log, so "the button doesn't work" reports have something
    to read.

- **Gothic II, through OpenGothic.** Gothic II is now a game profile of its own,
  managed the way Morrowind is managed through OpenMW: it appears in the game
  selector, is set up by pointing at your Gothic II folder (not an .exe) and
  your OpenGothic binary, and **Start** runs the engine with `-g` rather than
  the 2002 Windows exe under Wine. The setup finds the engine on its own
  wherever you keep it, including a build tree next to your games; pointing the
  folder picker at OpenGothic instead of the game is recognised, kept as the
  engine, and asked again for the game.

  Deploying is what makes Gothic mods load, and it follows three rules read out
  of the engine rather than guessed, each of which fails silently in game when
  it is wrong:

  - A `.mod` archive is thrown away unless it is named in the mod ini the engine
    was started with, and with no ini at all it throws away every one of them.
    So the deploy writes `system/Nerevarine.ini` listing exactly what it placed,
    and Start passes it with `-game:`. A total conversion's own settings (its
    GOTHIC.DAT, its starting world) are carried over from its ini.
  - Conflicts between archives are decided by the archive's own header
    timestamp, newest wins, whatever order they are mounted in. So load order is
    written by stamping those headers in list order, later in the list winning,
    the same rule the conflict view shows. The copy in your mods folder is never
    edited: the hardlink is broken first.
  - Mods ship in two shapes - the game's own layout (`Data/`, `system/`), which
    is copied in as-is, and a bare `Karibik.mod` with nothing around it, which
    is routed into `Data/` because the engine only ever scans there.

  Because Nexus offers no "Mod Manager Download" button for its Gothic 2
  section - it has no mod manager integration for that game, so no nxm:// link
  is ever generated for anybody - every file there is a manual download. With a
  Gothic profile active, the browser's download folder is watched: an archive
  landing there raises a banner offering to install it, one click, nothing
  automatic. Its Nexus file name carries the mod id, so the mod page is
  attached and the mod still gets update checks, which is what going manual
  otherwise costs you. No other game runs this, since everywhere else the
  nxm:// handler already does the job.

  Everything stays reversible through "Remove deployed mods", which takes the
  generated ini back out too. Note that OpenGothic still has no Ikarus/LeGo, so
  the mods that need those (Chronicles of Myrtana and friends) will not run
  whatever any mod manager does.

## Migration notes

- No state-format changes. Existing modlists, load orders, profiles and the
  light/dark theme choice carry over unchanged.
- An existing "Skyrim" profile keeps its id, mods folder, modlist and load
  order; only the label changes, to "Skyrim Legendary Edition (Oldrim)". Game
  labels now come from the game itself rather than from whatever was saved the
  first time, so a renamed game updates everywhere at once. Skyrim Anniversary
  Edition is a new, empty profile - nothing is moved into it.
- The BAIN picker only appears for archives whose top level is entirely
  numbered packages and that aren't FOMOD installers; everything else installs
  exactly as before.
