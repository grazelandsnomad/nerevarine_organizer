# 0.72 release notes

_In development._ Changes land here as they're committed; this file becomes the
GitHub release body when `v0.72` is tagged (release.yml reads it by version).

## New features

- **Check Updates notices when the file you installed has been retired.** It
  only compared the mod page's last change with your install date, so a file
  its page archived or replaced stayed "up to date" for as long as the page
  itself was quiet. Tamriel Data (HD) 25.05 read as current for a month
  after its page moved HD to a page of its own - until a Tamriel Rebuilt
  update needed the newer one and the game started warning at the main
  menu. The manager now remembers which Nexus file each mod was installed
  from, and Check Updates asks Nexus about that file. When it is archived,
  an old version or gone, the row gets an amber mark saying what the page
  offers now; click it to open the page. This covers mods installed from
  this version on: older installs never recorded their file.

- **Oblivion Remastered.** A Steam install is found on its own, and Deploy
  works for it. The remaster is the original engine inside Unreal 5, and three
  things differ from every other Bethesda game here. Its data sits five
  folders deep, in `OblivionRemastered/Content/Dev/ObvData/Data`. Its
  `Plugins.txt` lives in that Data folder and already lists the base game,
  the DLCs and the remaster's own `AltarESPMain.esp`, so a deploy adds your
  mods' plugins after that list instead of writing over it - done the usual
  way, the game would have lost its own. And some of its mods are not
  Bethesda files at all: Unreal `.pak` mods go to `Content/Paks/~mods`
  (UE4SS blueprint mods to `LogicMods`), OBSE64 plugins to
  `Binaries/Win64/OBSE`, and the OBSE64 loader beside the real game exe,
  wherever in the archive the mod kept them. Removing the deployment takes
  all of it back out and restores the game's list.

- **Mod-list backups now survive a clean of a source checkout.** A build run
  from a git clone keeps its state next to the binary, inside the checkout -
  and so did every backup of it, so one `git clean -xdf` took the mod lists
  and all twenty of their snapshots with them. Every snapshot is now also
  written outside the checkout, to
  `~/.local/share/nerevarine/Nerevarine Organizer/backups/`, and **Restore
  Modlist Backup** lists both places, so after a clean the button you already
  know brings the list back. The copy outside only takes a slot when the list
  actually changed, so the saves a session makes without changing anything
  cannot rotate the lost list out of it. A banner says all this once per
  checkout. AppImage and installed copies already keep their state outside
  any checkout and are unchanged.

## Bug fixes

- **Big installs no longer freeze the window.** Installing Tamriel Data (HD) -
  2.75 GB, some 54,000 files - showed "Not responding" for many minutes, long
  enough to be closed twice as crashed. Everything after the installer's
  questions ran on the window's own thread: copying every picked file one at a
  time, listing the destination folder again for each one, then deleting the
  unpacked archive. It runs in the background now, with a progress bar on the
  mod's row and a percentage in the status bar, and the window stays usable.
  A BAIN archive (packages like "00 Core") has its picked packages moved into
  place rather than copied, since the unpacked archive is thrown away
  afterwards. Measured on an NTFS mods drive with 54,000 files shaped like
  Tamriel Data's: copying them took five and a half minutes, and deleting the
  unpack half a minute more, with the window frozen throughout; moving them
  takes about a second. FOMOD installers still copy - an installer can put
  one file in several places - but no longer list the folder again for every
  file, nor wait for the drive to confirm each one (Qt's copy flushed every
  file to disk; an install now flushes once, at the end): the same 54,000
  files copy in 23 seconds. The unpacked archive is set aside and deleted in
  the background once the mod is in the list. A Merge into an
  existing mod runs in the background too. Closing the app while an install
  runs waits for it to finish, then closes, instead of leaving half a mod on
  disk.
- **Checking a download no longer freezes the window either.** A download
  that Nexus gave no checksum or size for has its archive tested with
  `7z t` before it is unpacked - a full decompression, up to half a minute -
  and that ran on the window's own thread. It runs in the background now,
  with the row saying "checking the archive"; removing the row meanwhile
  cancels it cleanly.
- **A FOMOD installer can no longer write outside the mod's folder.** A folder
  whose destination climbed out with `..` was meant to be refused, but the
  refusal came back as an empty path, which Qt reads as the folder the app was
  started from - so the files were copied there instead.
- **Updating or reinstalling a mod no longer scrambles the plugin load
  order.** While a mod was being reinstalled - an update, a Replace, a Merge -
  its old folder counted as gone, so every save during the install took its
  plugins out of the load order, with every plugin that needs them, and the
  install put them all back at the bottom when it finished. Reinstalling
  Tamriel Data moved 337 of 413 plugins: the game still started, since
  masters stayed ahead of their dependents, but the order you had arranged
  was gone. A mod being reinstalled now keeps its folder in the game until
  the new one lands. A plugin held back because its master is missing -
  say, while you reinstall that master some other way - keeps its place and
  goes back to it, instead of returning at the end. And the load-order file
  is now backed up before every change, as the mod lists are, and written in
  one piece.
- **Cancelling an update no longer uninstalls the mod.** Click Update on a
  mod, then Cancel in its installer or package picker, and the mod was
  marked "not installed" with its folder forgotten: its plugins left the load
  order, and after a restart it stayed uninstalled, its folder orphaned on
  disk. The same happened when an update's download, verification or
  unpacking failed, and to Reinstall from the right-click menu. An update or
  a Replace leaves the old folder untouched until the new one is in place, so
  the mod now simply stays installed, still marked as having an update.
- **Closing the app mid-update no longer loses the mod.** A mod being updated
  or replaced was saved as a download in progress, so if the app was closed
  or crashed before the install finished, it came back "not installed", with
  its folder left orphaned on disk and its notes, installer choices and
  load-order places gone. It is now saved as the installed mod it still is.
- **A plugin is no longer loaded twice when two folders ship it in different
  case.** Logs on Fire has `logs on Fire.esp` in its core folder and `Logs on
  Fire.esp` in its Apel's patch folder, the second meant to replace the first.
  OpenMW ignores case in plugin names, so the two are one file to it - but
  `openmw.cfg` listed both, and OpenMW loaded it twice, placing its objects
  twice. Plugin names are now compared as OpenMW compares them, so it is
  listed once; both folders stay, and the patch's copy is the one loaded.
- **A download is no longer thrown away when 7z or unrar is missing.** If
  the program needed to unpack an archive was not installed, the archive was
  deleted along with genuinely broken ones, so after installing the program
  the mod had to be downloaded again. It is kept now, and installing again
  uses it.
- **Undo no longer drops a "translation of" link you set by hand.**

- **Fixed the crash that could hit while checking for updates** - "QThread:
  Destroyed while thread is still running", the most frequent crash in the
  app's own log, at least eleven times since April. The background scan
  that works out which mods overwrite which could be deleted while it was
  still reading your mod folders, when a new scan was requested at the
  wrong moment; Check Updates made that moment likely, because it touched
  every row in the list at once. Only one scan now exists at a time, a
  request that arrives mid-scan is run straight after it instead of being
  dropped, and Check Updates no longer touches rows that have nothing to
  clear. The translation scan had the same flaw and has the same fix.
- **Installers no longer tick MGE XE next to OpenMW.** Some Morrowind
  installers ask which engine you use with checkboxes rather than a pick-one
  choice - OAAB_Data does - and the wizard's OpenMW rule only knew the
  pick-one kind. OpenMW got ticked for the wrong reason ("the mod is
  currently present in the modlist": it had found "OpenMW Quest Menu") and
  MGE XE was left ticked, so both options installed. OpenMW is now ticked as
  the engine this manager runs, MGE XE / MWSE / Code Patch options are
  unticked with a note saying what they are for, and an engine's name is
  never looked up as a mod.
- **Updating a mod no longer puts your old installer picks on the wrong
  options.** The wizard remembered picks by position, so when an update
  reordered its installer they landed elsewhere: OAAB_Data's picks from
  2.6.2 came back in 2.7.1 as MGE XE and Breton Knife-Ears. Picks are now
  remembered by name and found wherever the update moved them. A record from
  before this version that no longer fits the installer is set aside, and
  the wizard starts from its own recommendations instead.
- **"Your mod list has changed since it was last deployed" now means it.**
  It used to compare file times, and every save touches the list file -
  including the ones that change nothing, like switching games or quitting -
  so a list deployed and left alone claimed to have changed after the next
  restart. A deploy now records what it was made from (the enabled mods, in
  order, and the plugin load order), and the banner compares against that;
  reinstalling a mod into the same folder still counts as a change. A
  deployment made before this version keeps the old check until you deploy it
  once more.
- **Switching game no longer carries the old game's banner and count along.**
  Creating a new game straight after deploying another one showed the
  previous game's "changed since it was last deployed" over the new, empty
  list, with its "150 / 150 mods active" still in the corner. A game or
  profile that has never been saved now opens as a proper empty list.
- **Deploying during a temporary Size or Date sort uses your real order.** It
  deployed in the sorted order, which decides which mod wins a conflict.
- **Building from source no longer resets `nerevarine_prefs.ini`.** The file
  invites you to edit it, and `build.sh` copied the shipped one over it on
  every build, so a customised zoom range lasted until the next build. It is
  now written only when missing.

## Migration notes

- **The plugin load order is snapshotted like the mod lists**: each change
  keeps the previous `loadorder_<game>.txt` beside it as
  `loadorder_<game>.txt.bak.<date>-<time>`, the newest 20 of them.

- **Modlist rows gain an optional `"file"` key**, the Nexus file id a mod was
  installed from, written only when known. Older versions ignore it.
- **Installer choices are stored with their names.** A mod's `fomod` value in
  the modlist now reads like
  `0:0:0:Install%20Options/Game%20Engine/OpenMW`. Versions before 0.72 skip
  entries they cannot read rather than misapply them, so a list saved by
  0.72 and opened in an older version shows the installer's own defaults.
- **Source builds keep a second copy of each mod-list backup**, under
  `~/.local/share/nerevarine/Nerevarine Organizer/backups/<checkout>-<id>/`,
  with the same 20-snapshot limit. The largest list measured here is 106 KB,
  so that is a few MB at most. Nothing is written there for AppImage or
  installed builds.
